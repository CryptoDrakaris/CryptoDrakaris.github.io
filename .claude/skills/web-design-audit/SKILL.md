# Web Design Audit

Проверка готового сайта по сводному своду правил web-дизайна. Правила адаптированы из двух открытых проектов:

- [ui-ux-pro-max-skill](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill) (MIT, © 2024 Next Level Builder) – объективные нормы: взяты правила, применимые к вебу, нативные (жесты, вибро, safe area, Dynamic Type) убраны, добавлены SEO, мультиязычность и проверки для статических сайтов;
- [taste-skill](https://github.com/Leonxlnx/taste-skill) (MIT, © 2026 Leonxlnx) – категория «Шаблонность и вкус»: взяты правила, не привязанные к стеку (React, Tailwind, Motion отброшены) и не спорящие с каноном бренда и типографикой языка.

Аудит **не выбирает стиль** и не предлагает сменить фирменную палитру или шрифты. Если у проекта есть канон (CLAUDE.md, дизайн-система, брендбук), он считается заданным: проверяется, соблюдён ли он последовательно и не нарушает ли правила доступности. Если фирменный цвет не проходит по контрасту, предлагай изменить его применение (крупный текст, фон кнопки, декоративная роль), а не сам цвет.

## Файлы

- `references/rules.md` – полный свод правил: ID, приоритет, способ проверки. Читать перед аудитом целиком.
- `scripts/audit-static.mjs` – статическая проверка готового HTML и CSS (Node 18+, без зависимостей). Флаг `--no-taste` отключает категорию «Шаблонность и вкус».
- `scripts/taste-checks.mjs` – механические проверки категории «Шаблонность и вкус» (подписи над заголовками, декоративная нумерация, три одинаковые карточки, перегруз первого экрана и др.), вызывается из `audit-static.mjs`.
- `scripts/browser-checks.js` – выражение для выполнения в открытой странице: реальный контраст текста, размеры целей, переполнение, мелкий текст, длина строки, перекрытие фокуса липкой шапкой, тяжёлые картинки.

## Порядок работы

### 1. Контекст

- Определи стек по `package.json` и структуре. Для статических генераторов (Astro, Next export, Eleventy, Hugo) аудит идёт по **собранному** HTML: найди команду сборки и папку результата (`dist/`, `out/`, `build/`, `_site/`).
- Прочитай правила проекта (CLAUDE.md, дизайн-систему): палитра, шрифты, языки, ограничения. Это эталон для категории «Стиль и последовательность».
- Уточни у пользователя только то, что нельзя вывести: какие страницы важнее, если сайт большой (больше ~30 шаблонов).

### 2. Статическая проверка

Собери проект, если сборка устарела, затем:

```bash
node .claude/skills/web-design-audit/scripts/audit-static.mjs <папка-сборки> [--css путь/к/токенам.css]
```

Скрипт проходит все `.html`, извлекает CSS из файлов и `<style>`, группирует одинаковые находки по всем страницам. Результат – список находок с ID правил и таблица контраста цветовых токенов. `--json` для машинного вывода.

Скрипт делает эвристику по разметке, а не полноценный парсинг. Каждую находку уровня CRITICAL и HIGH подтверждай по исходнику, прежде чем включать в отчёт. Ложные срабатывания отбрасывай молча, спорные помечай «проверить».

### 3. Проверка в браузере

Запусти dev-сервер или preview проекта и открой его доступным браузерным инструментом. Если браузера нет, пропусти шаг и явно напиши в отчёте, что runtime-проверки не выполнялись.

Для каждого **типа** страницы (главная, список, карточка, статья, контакты и т. п., по одной на шаблон) и для каждого языка, если их несколько, на ширинах **375, 768, 1024, 1440**:

1. Выполни содержимое `scripts/browser-checks.js` в странице (прочитай файл и передай его текст в инструмент выполнения JS). Он вернёт JSON с находками.
2. Сделай скриншот первого экрана и прокрученной середины. Смотри глазами: иерархия, выравнивание, ритм отступов, обрезанный или налезающий текст, пустоты, «прыгающие» элементы.
3. Клавиатура: пройди Tab по шапке и основному контенту хотя бы на одной странице. Фокус виден на каждом элементе, порядок совпадает с визуальным, скип-ссылка появляется первой, меню открывается и закрывается с клавиатуры.
4. Интерактив: фильтры, меню, переключатели языка – сработать, проверить состояние после «Назад» в браузере.

После проверки верни окно браузера к исходному размеру.

### 4. Ручной проход по коду

По `references/rules.md` пройди правила с пометкой **[C]**: семантика компонентов, состояния hover/focus/active, токены вместо сырых цветов, анимации только transform/opacity, `set:html`/`innerHTML` только для доверенного контента, формы.

### 4a. Шаблонность и вкус

Раздел 11 `rules.md`. Сначала перечитай его ограничения, затем:

1. Возьми находки `taste-*` из статического скрипта и отсей те, что противоречат ограничениям: приём взят из канона бренда, тире в RU/KK тексте, разрешённое в CLAUDE.md.
2. По скриншотам из шага 3 пройди правила с пометкой **[V]**: ритм секций, плашки на картинках, цветные точки, засечки, «острова» другой темы, единый акцент и форма.
3. Для каждой оставшейся находки предложи исправление в терминах текущего стека проекта, без новых фреймворков и библиотек.

Находки этого раздела никогда не бывают CRITICAL или HIGH. Если пользователь не просил оценку вкуса отдельно, выводи их в отчёте последним разделом «Шаблонность и вкус», чтобы они не смешивались с нарушениями доступности и производительности.

### 5. Отчёт

Отвечай на языке пользователя. Структура:

```
## Аудит web-дизайна: <проект>, <дата>
Охват: N страниц/шаблонов, языки, ширины; что не проверялось и почему.

| Приоритет | Находок |
|-----------|---------|
| CRITICAL  | … |
| HIGH      | … |
| MEDIUM    | … |
| LOW       | … |

### CRITICAL
1. **<rule-id>: короткое название** – где (`файл:строка` или URL + ширина). Что не так, с цифрами (контраст 3.1:1 при нужных 4.5:1). Как исправить – конкретно, для этого кода.

### HIGH / MEDIUM / LOW – так же

### Шаблонность и вкус
Находки раздела 11 отдельным списком, с пометкой MEDIUM/LOW. Для каждой – почему не срабатывает ограничение (канон бренда, язык, стек).

### В порядке
Коротко по категориям: что проверено и соответствует.
```

Правила отчёта:

- Одна находка – одна проблема. Одинаковая проблема на многих страницах – одна находка со списком мест.
- Всегда цифры, где правило числовое: коэффициент контраста, размер цели в px, ширина переполнения, вес файла.
- Не выдумывай находки ради полноты. Пустой раздел – это нормально.
- Не завышай приоритет: CRITICAL – только то, что блокирует использование (недоступно с клавиатуры, нечитаемо, отключён зум, нет alt у содержательных изображений, контраст основного текста ниже 3:1).

### 6. Исправления

По умолчанию аудит только отчитывается. Исправляй, если пользователь попросил («проверь и исправь», «--fix») или подтвердил после отчёта. После правок пересобери проект и повтори проверки, которые затронуты, и отметь в отчёте, что исправлено, а что осталось.
